# Alternate mockups

Self-contained HTML. Open in a browser; no build, no server, no network.

These are in the repository for one reason: **an agent that cannot see them will
re-derive the decisions in them, differently.** They were originally published as
chat artifacts, which the other agent cannot read.

Read-only design inputs, not production code. The rule in
`docs/decisions/0010-prototype-before-production-ui.md` applies — prototype code
is not promoted; production is reimplemented against the real architecture.

| File | What it shows |
|---|---|
| `hipaa-assessment-workspace.html` | HIPAA assessment surface, preserving the historical 192-record catalog snapshot used during prototyping |
| `cmmc-assessment-workspace.html` | CMMC Level 2 surface, running on the real 110 requirements and 320 objectives |
| `v1-build-map.html` | The remaining V1 slices in dependency order |

**Superseded HIPAA prompt behavior:** the historical HIPAA mockup predates the
approved Privacy role filter. It renders every raw Privacy child paragraph as a
checkbox. That behavior is known incorrect and must not be reused. Production
classifies entries as assessment checks, applicability notes, or context; only
assessment checks render checkboxes. It also leaves all Security questions on
the parent standard; production routes NIST-labelled questions to their
implementation specification and retains only genuinely standard-wide guidance
on the parent.

## What the two workspaces are arguing

They are deliberately different shapes, and that difference is the point.

**CMMC is requirement-centred.** A requirement fills the surface with all of its
assessment objectives visible together, each carrying its own determination. That
matches how the gap analysis is actually run — walking `3.1.1[a]` through `[f]`
with the client in one sitting.

**HIPAA is record-at-a-time.** Its units are coarser: 82 standards over 108
implementation specifications, against CMMC's 110 over 320. There is no
equivalent of walking three objectives in a minute.

Under ADR 0012 these are **two presentation modes of one workspace**, not two
screens. Building them as two screens would violate that decision.

## What they were built to test

Five things the earlier prototype on `codex/v1-ui-prototype` left open:

1. **Citations are the identifiers.** Every record is addressed by its published
   identifier — `164.308(a)(1)(ii)(A)`, `AC.L2-3.1.1[a]`. The earlier prototype
   minted `SRA-01` and `PRIV-01`, which cannot be cited in a report and which
   `docs/specification.md` forbids.
2. **The determination set is complete per framework.** HIPAA carries N/A with
   rationale and the addressable decision required by 45 CFR 164.306(d)(3).
   CMMC does not, because CMMC has no addressable concept.
3. **Rollup is displayed and never edited.** A parent's status is derived from
   its children with the reason stated.
4. **Navigation was exercised at real scale** — the then-current 192-record HIPAA snapshot and 320 CMMC objectives rather than four
   fixtures. Search, filters, and `j`/`k` movement.
5. **Guidance sits with the record it belongs to**, attributed to its source and
   carrying no status of its own.

## Provenance of the embedded data

Both workspaces embed real catalog data so navigation is tested honestly rather
than against fixtures.

- HIPAA records come from `catalog/versions/hipaa-45cfr164-2026-07-01.json`.
- HIPAA prompts come from `catalog/spikes/prompts-sample.json` — the issue #29
  sample, populated for one standard and honest about the rest.
- CMMC requirements and objectives come from the CMMC Assessment Guide Level 2.
- CMMC evidence types, examples and assessment considerations come from
  RainTech's own assessment worksheet, and are labelled as practitioner guidance
  rather than DoD or NIST content. A report must never cite them as authority.

**No client data.** The CMMC source workbook contains a real client's name,
address and telephone number in an SSP template scaffold. Only four per-objective
columns were read, all keyed by objective identifier; the scaffold rows carry no
objective identifier and were never touched. Both files were scanned against the
known identifiers before being committed.

## Known gaps

Recorded so they are not mistaken for finished thinking.

- **No evidence attachment.** Neither workspace can map evidence to a record,
  because Evidence is Slice 5 and both assessment surfaces are earlier. Tracked
  as an open question in `PROJECT_STATUS.md`.
- **Control-first only.** Both assume work arrives one record at a time. One
  interview touches many records, and there is no path for that here.
- **CMMC shows no score.** The DoD Assessment Methodology point values are not
  ingested, and `docs/specification.md` forbids inventing a generic readiness
  score. Counts are shown; a score is not.

## Regenerating

These were generated by embedding catalog JSON into a static page. They are not
built by CI and will not update themselves when a catalog changes — if a catalog
is re-ingested, the embedded copy here goes stale. That is acceptable for a
design input and would not be for anything else.
